# Verification record

**What this is.** Evidence that the nine defects raised by the external audit
were fixed, and that fixing them did not change any result the report depends
on. It records what was actually run and what came back, not what was intended.

**Scope.** The audit validated the science - the model, the reward, the
observation space, the experimental design - and none of those were touched.
Every change here is to correctness of tooling, reproducibility, or accuracy of
documentation.

Sections 1 to 4 cover the nine defects the audit raised. Section 5 covers three
more found in the follow-up work itself, before it produced a published number;
they are here because two of the three would have failed silently.

**Dates.** Remediation 7-8 September 2026, against the tree tagged
`pre-remediation-audited`.

## 1. Headline result

**The re-run evaluation reproduced the original numbers exactly.** All 150
episodes are bit-for-bit identical to the committed results across all eleven
recorded metrics. Not "within stochastic noise" - identical.

That is the expected outcome and the reason it is a strong check: an episode is
fully determined by `(controller, scenario, seed)`, and the remediation changed


from the re-run data, which is the same statement made from the other end.

### D1 — Route generation was not reproducible

`networks/generate_routes.py` seeded from `hash((scenario, seed))`. Python
salts string hashing per process, so the same command produced different
traffic on every run.

**The failure, reproduced before fixing** (three fresh interpreters, same
scenario and seed):

```
ns_heavy_seed100  vehicles=1759  sha256=87f7d8c223546767  first=E2C_0 …
ns_heavy_seed100  vehicles=1759  sha256=e273676aca655ef1  first=S2C_0 …
ns_heavy_seed100  vehicles=1867  sha256=f3234ad60916c642  first=W2C_0 …
```

Three different hours of traffic, and even a different vehicle count.

**After the fix** (`zlib.crc32` of `"<scenario>_<seed>"`), three fresh
interpreters:

```
ns_heavy_seed100  vehicles=1748  sha256=7d1314eeba87edaf  first=N2C_0 …
ns_heavy_seed100  vehicles=1748  sha256=7d1314eeba87edaf  first=N2C_0 …
ns_heavy_seed100  vehicles=1748  sha256=7d1314eeba87edaf  first=N2C_0 …
```

A different scenario at the same seed number still yields different traffic
(`balanced_seed100` → 1620 vehicles), so the scenario name is still mixed in.

**An honest limitation, stated plainly.** The committed route files were
generated by the *old*, salted code. They therefore cannot be regenerated by
the fixed generator — note that 1748 above is not the committed file's 1783.
The committed files remain authoritative for every published number, which is
why the generator now refuses to overwrite them:

```
$ python networks/generate_routes.py
Refusing to overwrite 40 existing route file(s) in …/networks/routes.
…
$ echo $?
1
$ git status --short networks/routes | wc -l
0
```

Regenerating requires an explicit `--force` and, to stay honest, retraining and
re-evaluating. Guarded by `tests/test_route_determinism.py`, which pins the
seed to its literal CRC value so a return to any process-dependent function
fails immediately.

### D4 — The report claimed a provenance guarantee it did not have

Confirmed false before fixing: none of the eight table blocks written by
`make_tables.py --write` appeared anywhere in `REPORT.md`.

Fixed by the preferred route. Four tables now sit between paired
`BEGIN GENERATED` / `END GENERATED` comments and are spliced in by
`make_tables.py --write`. The splice is idempotent (same md5 on a second run)
and fails loudly on a missing or unpaired marker rather than writing a
half-updated report. `tests/test_report_matches_data.py` closes the loop by
parsing the numbers back out of the committed markdown and checking them
against the CSVs, so the §8 claim is now enforced rather than asserted.

The §8 wording was also corrected: it previously said *every* number is
generated, which overstated the mechanism, since figures quoted in the prose
are still read off the tables by hand.

### D5 — `MIN_GREEN` defined twice

`baseline/fixed_time.py` now imports it from `eval/simulation.py` alongside
`YELLOW_TIME`. `test_min_green_is_not_defined_twice` asserts the two names are
the same object, so a re-introduced copy fails the suite.

### D6 — The honesty metric failed silently to zero

`run_episode` read the insertion backlog inside a bare
`contextlib.suppress(Exception)`, so a failed measurement produced `0` — the
same value that means "no demand was dropped", which is exactly the reading
§5.2 of the report relies on.

Now catches `traci.TraCIException` only, prints a warning naming the episode,
and records the sentinel `-1`. `eval/evaluate.py` surfaces any `-1` as an
explicit warning before the honesty summary, and
`test_the_insertion_sentinel_survives_a_round_trip` checks it is not flattened
to 0 by the CSV round-trip.

The metric was also relabelled throughout, since it is a snapshot of the
backlog at t=3600 rather than a per-hour count. See §4 for the resulting
wording change in the report.

### D7 / D8 — Documentation and constants

`train_dqn.py` now states ~46 min (logged: 45.9) and `train_ppo.py` ~26 min
(logged: 26.0); they had each other's figures. `agent/training.py` imports
`N_INCOMING_LANES` instead of hard-coding `8.0` — it is the constant the reward
divides by, so a literal there would silently mislabel every training curve.

### D9 — Packaging and hygiene

Added `pyproject.toml` (Python floor, pytest and ruff configuration).
`_quiet_stdout` renamed to `quiet_stdout`, since it is used across a package
boundary. `EpisodeLogger.algo`, previously assigned and never read, now labels
the progress lines.

**One item downgraded, with justification.** The audit flagged `pandas` as an
unused pin. It is unused by *this project's* code, but it is a hard runtime
requirement of both `sumo-rl` and `stable-baselines3`:

```
sumo-rl            -> ['pandas']
stable-baselines3  -> ['pandas']
```

Dropping the pin would not remove the dependency, only unpin it — trading
reproducibility for nothing. It is kept, moved to a clearly labelled
"pinned transitive dependencies" section explaining why.

**One item deliberately not fixed.** `run_episode` still builds a throwaway
controller via `controller_factory(None)` to read the `uses_env_control` class
attribute. Removing it means changing the factory contract across four call
sites for a cosmetic gain, on the one code path every published number flows
through. The instantiation is free (no controller does work in `__init__`) and
is explained by a comment. Not worth the risk during a remediation pass.

## 4. Numbers that changed, and why

Three changes to `REPORT.md`. **No measured value changed** — every difference
below is a rounding correction, a relabel, or added rows.

**1. `ns_heavy` in the greedy-vs-DQN table: "8% better" → "7% better."**
Greedy 22.29 s, DQN 20.64 s. Expressed relative to the worse controller, as
every other row in that table is, the gap is 7.4% → 7%. The hand-written 8% was
inconsistently rounded. This is precisely the drift D4 predicted, and it was
found by generating the table rather than by reading it.

**2. The insertion-backlog table gained three rows and a new column label.**
Previously it listed only the four largest values; the generator emits every
non-zero mean, which adds `ns_heavy`/fixed-time (5) and `ew_heavy`/fixed-time
(4), and names the controllers in full. The header changed from
"Vehicles not inserted (mean per hour)" to "Still awaiting insertion at the
hour's end (mean)", per D6. The two figures the report's argument rests on are
unchanged: 227 on `surge`, 95 on `peak`.

**3. §5.2 and the appendix wording.** §5.2 now states that the figure is a
snapshot at t=3600 rather than a running count, and the appendix entry records
the `-1` sentinel. The argument is untouched: the untuned plan still fails to
admit ~10% of `surge` demand, and its reported waiting time is still an
underestimate of its true cost.

One further difference, in the data rather than the report: in
`evaluation_summary.csv` the `vehicles_not_inserted_max` column now prints `0`
where it printed `0.0`, in 24 rows. This is the append-mode type artefact the
audit noticed (PPO's rows differed from the rest) resolving itself now that
every row comes from one fresh sweep. Zero numeric values differ.

## 5. Defects found in the follow-up work itself

These are not audit findings. They are bugs in the Phase 3 code — the extra
training seeds, the mixed-demand agent, the longer PPO run and the safety
wrapper — caught before any of it produced a published number. They are
recorded here rather than quietly fixed because three of the four would have
failed *silently*, which is the failure mode this whole document exists to
argue against.

| ID | Defect | Would have | Status |
|---|---|---|---|
| F4 | **The safety wrapper enforced nothing** | Published a false safety claim | **Fixed & tested** |
| F1 | Safety wrapper crashed on a fixed-time plan | Blocked one row entirely | **Fixed & tested** |
| F2 | Trace filename built three ways, two disagreed | Published a short table | **Fixed & tested** |
| F3 | Generated table looked up an unknown controller | Crashed the last step | **Fixed & tested** |

F4 is listed first because it is the one that mattered. The other three would
have produced a visibly broken artefact or none at all; F4 would have produced
a complete, plausible, confident section asserting a safety property the
controllers did not have.

### F4 — the safety wrapper enforced nothing

The most serious of the four, and the one that would have been believed.

`SafetyConstrainedController` reset a phase's starvation clock when the wrapped
controller **asked** for that phase. Asking is not being served: sumo-rl refuses
a phase change while the current green is younger than `yellow + min_green`, so
a controller can request a phase every few seconds and never receive it. Every
refused request reset the clock, the bound was never reached, and the wrapper
passed every action through untouched.

**Measured on one `balanced` hour, with the wrapper in force:**

```
the phase asked for was not the phase then green : 573 of 720 decisions
the wrapper's own worst "unserved" clock         : 175 s   (bound: 200 s)
starvation overrides fired                       :   0
max-green overrides fired                        :   0
longest a phase actually went unserved           : 245 s
```

The wrapper reported compliance, at 175 s against its 200 s bound, while the
junction left a movement dark for 245 s. `greedy-queue+safe` produced a trace
**bit-identical** to `greedy-queue`, which is what a wrapper that never fires
looks like from the outside — and it had been read as "the policy was already
safe."

**The fix.** `_observe()` now advances the clocks from `signal.green_phase` —
the phase actually showing green — at each decision, and amber resets nothing
because during amber no phase has right of way. The request the wrapper makes
this step is not credited to anything; if it is refused, the clock keeps
climbing and the wrapper keeps asking until it is granted.

**What that changed, on the trace seed:**

| Controller | Longest a phase went unserved, unwrapped | Wrapped |
|---|---|---|
| Greedy queue, `balanced` | 245 s | **215 s** |
| Greedy queue, `ns_heavy` | 320 s | **215 s** |
| DQN, `balanced` | 280 s | **210 s** |
| DQN, `ns_heavy` | 315 s | **210 s** |

against a 200 s bound with up to 45 s of forced hand-over slack. The cost was
under half a second of mean waiting time, and on `ns_heavy` both controllers
were *faster* wrapped than unwrapped.

**Two consequences for the report.** The unconstrained policies were not
already safe — they violated the starvation bound on every scenario checked, by
between 45 and 140 seconds. And addendum E's conclusion is now derived from the
traces rather than asserted in prose: the earlier version hard-coded the
sentence "it serves every phase well inside 200 s" into the branch that fires
when the constraint is cheap, so it would have printed that claim over data
that contradicted it. `tests/test_followups.py` now covers both branches.

**Why the tests did not catch it.** The stub signal simply did what it was
told, so "asked for" and "served" were the same thing and the bug was invisible
by construction. `tests/test_safety_constraints.py` now models sumo-rl's
refusal window, and `drive()` returns what the signal **served** rather than
what was requested; every guarantee is asserted against that sequence.
`test_a_refused_request_does_not_count_as_a_service` pins the accounting in its
smallest form, and `test_a_phase_asked_for_but_never_served_still_trips_the_bound`
drives an adversarial controller that asks for a phase only at the moments the
signal will refuse it.

That is the general lesson of this one: a test double that is more obedient
than the system it stands in for will certify behaviour the real system does
not have.

### F1 — the safety wrapper could not wrap a fixed-time plan

`SafetyConstrainedController.on_episode_start` read
`len(signal.green_phases)`. sumo-rl builds that list only when it is driving
the signal itself; under a fixed-time plan SUMO runs the program and the
attribute does not exist.

```
AttributeError: 'TrafficSignal' object has no attribute 'green_phases'.
  eval/simulation.py:399  in on_episode_start
```

So `dqn+safe` ran perfectly and `fixed-time-tuned+safe` could not be evaluated
at all — a shape of bug that only shows up on the controller nobody tried
first. Fixed by reading `num_green_phases`, which sumo-rl publishes in both
modes and is the quantity actually wanted.

This is the loud one of the four: it raised. It is recorded because of what
the fix had to guard. The stub in `tests/test_safety_constraints.py` now
deliberately publishes `num_green_phases` and **not** `green_phases`, so every
test in that module exercises the fixed-time shape, and
`test_the_wrapper_starts_on_a_signal_sumo_is_driving` asserts the absence
explicitly — a stub carrying both attributes would have passed either way and
proved nothing.

### F2 — the trace filename was built in three places, and two disagreed

`eval/evaluate.py` wrote the per-episode traces; `eval/make_plots.py` and
`eval/followups.py` read them back. Each built the filename itself. They agreed
until the `+safe` suffix arrived:

```
written by evaluate.py :  trace_greedy_queue+safe_ns_heavy.csv
sought by followups.py :  trace_greedy_queue_safe_ns_heavy.csv
```

Nothing raised. A missing trace is a legitimate state — most controllers have
no trace for most scenarios — so `trace_bounds` returns `None` and the row is
skipped. Addendum E would have been published with the constrained controllers
**missing from the one table that exists to show them**, and the table would
have looked complete.

Fixed by `eval/paths.py`: one naming function, imported by all three scripts.
`tests/test_output_naming.py` checks the contract from both ends — identity of
the function object across the three modules, so a fourth copy cannot be
reintroduced, and a round trip that writes a trace with `evaluate.write_trace`
and requires `followups.trace_bounds` to find it.

### F3 — a generated table would have crashed on the new controller names

`insertion_backlog_table` iterated every controller in `evaluation_raw.csv` and
looked each one up in `LABELS`, which knows only the report's five. Once
`dqn_seed2`, `dqn_mixed` or `dqn+safe` appeared in that file with a non-zero
insertion backlog — which the saturated scenarios make likely — it would have
raised `KeyError` at `make_tables.py --write`, the very last step of the
pipeline, after several hours of training and evaluation had already run.

The table is now restricted to the five controllers it describes, like every
other generated table in the report. That is also the right answer on the
merits: the addendum variants belong in their own addendum, not in a section 5
table a reader would try to match against the five-row comparison above it.

### Two further corrections found the same way

**The PPO addendum judged a closed gap on `abs()` of a signed gap.** If the
longer run had overtaken the DQN, the gap would have gone negative and the
generator would have reported a large *remaining* deficit — the opposite
conclusion, stated confidently. The comparison is now on signed values, an
overtake gets its own sentence, and `tests/test_followups.py` covers all three
branches.

**Addendum D's table had a five-column header over a four-column divider**,
which renders as a mangled table in every markdown viewer. Found by a test that
checks every generated table for a header/divider/row column-count match, not
by reading the output.

### Why `fixed-time-tuned+safe` is reported as a null

Related to F1, and worth stating because the honest answer is less impressive
than the convenient one. A fixed-time plan is run by SUMO's own program, so the
wrapper's `act()` is never consulted and its `+safe` run is bit-identical to
the unwrapped one **by construction**. Confirmed directly:

```
fixed-time-tuned+safe  wait 31.23  switches 119  throughput 1746
fixed-time-tuned       wait 31.23  switches 119  throughput 1746
```

Presenting that zero as evidence that the plan satisfies the bounds would be
reading a tautology as a measurement. The run is still done and still reported,
labelled as an inert wrapper, and the plan's actual compliance is established
from its recorded light strings instead.

## 6. How to re-verify

```bash
python -m pytest                     # 497 tests, ~1 s
python -m ruff check .               # lint, rule set pinned in pyproject.toml
python smoke_test.py                 # toolchain, 5 checks
python eval/evaluate.py              # ~26 min; must reproduce the CSVs exactly
python eval/make_tables.py --write   # must leave REPORT.md byte-identical
python eval/make_plots.py            # four figures, byte-identical
```

The last three are the strong ones: if the evaluation is re-run and the
report's tables or the figures change, something has moved that should not
have.

The addenda regenerate from the same data and are also idempotent:

```bash
python eval/significance.py --write  # addendum A
python eval/followups.py --write     # addenda B-E
```

Neither touches sections 1-9; each rewrites only its own marked region, and
`eval/make_tables.py --write` afterwards must still leave sections 4 and 5
byte-identical. That is the check that an addendum has not quietly moved a
number in the original report.
